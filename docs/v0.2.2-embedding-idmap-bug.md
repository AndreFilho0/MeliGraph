# Bug: Acoplamento entre payload de embeddings e IdMap (planejado para v0.2.2)

> **Status:** identificado em v0.2.1, fix planejado para v0.2.2.
> **Severidade:** alta. Quebra silenciosamente o fluxo "treina → persiste binary →
> recarrega em boot fresco" que o próprio README documenta como caso de uso
> principal do LightGCN.

---

## Sintoma

Em produção, depois de:

1. Treinar via `MeliGraph.train_embeddings/2` num job noturno
2. Persistir o `binary` retornado em Postgres / R2 / S3
3. **No boot do app**, carregar o último binary com `MeliGraph.load_embeddings/2`
4. Chamar `MeliGraph.recommend(:feed, "profile:5", :content, algorithm: :lightgcn)`

Observa-se:

```elixir
MeliGraph.edge_count(:feed)
# => 0      (grafo em memória ainda vazio — não foi repopulado no boot)

MeliGraph.embeddings_ready?(:feed)
# => true   (payload carregado com sucesso)

MeliGraph.recommend(:feed, "profile:5", :content, algorithm: :lightgcn, top_k: 10)
# => {:ok, []}    (vazio, mesmo sabendo que profile:5 estava no payload)
```

Pior: o fallback transparente para SALSA (que existe pra cobrir
"embeddings não prontos") **não dispara**, porque o erro retornado é
`{:ok, []}` e não `{:error, :embeddings_not_ready}`.

---

## Investigação — três camadas do bug

### Camada 1 — `Query.compute_inline/4` cura o external_id antes de delegar

`lib/meli_graph/query/query.ex:59`:

```elixir
defp compute_inline(conf, external_id, type, opts) do
  algorithm = resolve_algorithm(Keyword.get(opts, :algorithm, :pagerank))

  result =
    if global_algorithm?(algorithm) do
      algorithm.compute(conf, 0, type, opts)
    else
      case IdMap.get_internal(conf, external_id) do
        nil ->
          {:ok, []}                                        # ← curto-circuito
        internal_id ->
          algorithm.compute(conf, internal_id, type, opts) # ← passa internal_id
      end
    end
  ...
end
```

Em boot fresco, `IdMap` está vazio porque ele só popula via `insert_edge/5`.
`get_internal/2` devolve `nil` → query retorna `{:ok, []}` antes mesmo de
chamar `Algorithm.LightGCN.compute/4`. Sem chamada → sem erro
`:embeddings_not_ready` → sem fallback.

### Camada 2 — Payload do `EmbeddingStore` é keyed por internal_id

`lib/meli_graph/lightgcn/embedding_store.ex` (formato do payload v1):

```elixir
%{
  version: 1,
  embeddings: Nx.Tensor.t(),
  user_index: %{internal_id => row_index},   # ← keyed por internal_id
  item_index: %{internal_id => row_index},   # ← keyed por internal_id
  user_count: ...,
  item_count: ...,
  trained_at: ...
}
```

`internal_id` é um inteiro produzido pelo `IdMap` da instância **no momento
do treino**. Sem o `IdMap` daquele momento, esses inteiros não
significam nada — são opacos.

### Camada 3 — `IdMap` é ordem-dependente, não determinístico

`lib/meli_graph/graph/id_map.ex:101`:

```elixir
internal_id = :atomics.add_get(state.counter, 1, 1) - 1
```

Counter incremental atribui IDs na ordem em que `insert_edge` é chamado.
Reinserir no boot na **mesma ordem** funciona; em ordem diferente
(`Repo.all` sem `order_by`, `Task.async_stream` no pipeline, mudança no
schema da query) → mesmo external_id ganha internal_id diferente →
`embeddings[5]` que era `profile:5` no treino vira `profile:42` em runtime.

**Recomendações silenciosamente trocadas, sem nenhum log de erro.** Pior
classe de bug pra um sistema de recomendação.

---

## Por que os testes não pegaram

`test/meli_graph/lightgcn/embedding_store_test.exs` e
`test/meli_graph/query/lightgcn_integration_test.exs` sempre populam o
grafo **antes** de carregar embeddings, e na **mesma instância** onde o
treino aconteceu. Nesses cenários, o `IdMap` está coerente com o payload
porque foi o mesmo `IdMap` que produziu os internal_ids ali presentes.

O cenário "instância vazia + payload externo" — exatamente o fluxo
documentado no README pra LightGCN — nunca foi exercitado nos testes
unitários nem nos de integração.

---

## Fix planejado — v0.2.2

A solução é **eliminar a dependência do `IdMap` no caminho de inferência**,
fazendo o payload do `EmbeddingStore` carregar `external_id => row_index`
em vez de `internal_id => row_index`. Custo de memória é desprezível
(strings tipo `"profile:42"` ~10 bytes vs ints ~8 bytes — payload cresce
~20% no pior caso).

### Mudanças concretas

1. **`MeliGraph.LightGCN.Matrix`**
   - `partition_nodes/2` retorna `users / items` keyed por **external_id**
   - `collect_weighted_pairs/3` traduz internal→external uma vez ao ler os
     segments (via `IdMap.get_external/2`)
   - `positive_pairs` continua como `{user_row, item_row}` — usado só pelo
     Trainer pra sampling, não toca em IDs externos

2. **`MeliGraph.LightGCN.EmbeddingStore`**
   - `valid_payload?/1` aceita maps de external_id (qualquer term)
   - **Bumpa `version: 1 → 2`**
   - Payloads `version: 1` antigos → rejeitar com `{:error, :payload_version_unsupported}`
   - Migração on-the-fly do v1 → v2 não é viável: precisaria do `IdMap`
     daquela época, que justamente não temos

3. **`MeliGraph.Algorithm.LightGCN`**
   - `score_user/4` recebe **external_id direto** (não mais internal_id)
   - `Map.get(u_idx, external_id)` em vez de `Map.get(u_idx, entity_id)`
     com entity_id ambíguo
   - **Remove o `IdMap.get_external/2`** no final do `score_user` — chave
     do `i_idx` já é o external_id

4. **`MeliGraph.Query.compute_inline/4`**
   - Não pode mais cortar pra `{:ok, []}` quando `IdMap.get_internal` é `nil`
   - Forma proposta: behaviour `Algorithm` ganha callback opcional
     `requires_internal_id?/0` (default `true`). LightGCN sobrescreve pra
     `false`. Query inspeciona e decide se traduz ou passa external_id direto

5. **Testes — regression guards obrigatórios**
   - **`embedding_store_test`**: caso "boot fresco — instância vazia,
     carrega payload, recomenda corretamente"
   - **`lightgcn_integration_test`**: caso "treina em instância A, carrega
     payload em instância B (vazia), recomenda corretamente em B"
   - **`matrix_test`**: caso "ordem de inserção diferente entre dois grafos
     produz mesmo `user_index/item_index` no payload" (determinismo)

## Migração para usuários da lib

Payloads `version: 1` produzidos por v0.2.0 ou v0.2.1 **deixam de funcionar**
em v0.2.2. Não há migração on-the-fly. O caller precisa:

1. Atualizar `meli_graph` para `~> 0.2.2`
2. Disparar um treino fresco (`MeliGraph.train_embeddings/2`)
3. Persistir o novo binary (`version: 2`)
4. Apagar/sobrescrever o binary antigo
5. Restartar o app — `load_embeddings/2` agora aceita o novo payload

Como recomendações personalizadas dependem de retrain frequente em produção
(no mínimo diário), o impacto operacional é baixo: a próxima rodada do job
noturno já produz payload compatível.

---

## Por que `v0.2.2` e não `v0.3.0`?

Tecnicamente é breaking change (formato de payload, behaviour `Algorithm`).
Pelo SemVer estrito, mereceria `0.3.0`. A escolha de empacotar como
`0.2.2` é deliberada: o projeto está pre-1.0 (`0.x`), e a v0.3 já está
reservada no roadmap pra mudanças maiores (matriz sparse, retreino
incremental, pesos no PageRank/SALSA). Empurrar essa correção pra dentro
da v0.3 atrasa o fix de um bug **crítico** sem ganho real — pacote v0.2.x
continua sendo "LightGCN denso, peso só no LightGCN". v0.2.2 é
patch-spirit (fix de bug), mesmo que tecnicamente não seja patch-pure.

A nota do CHANGELOG/README para v0.2.2 deixa o breaking change explícito:
quem ler vai entender que precisa retreinar.
